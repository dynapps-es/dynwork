# Local systemprompt 0.76 instances

Two disposable instances of `ghcr.io/systempromptio/systemprompt-dynapps:0.76.0` (`alpha` and `beta`) on one
PostgreSQL 18, for every DynWork phase that needs a real server. They never reach a Dynapps environment. Everything
binds to `127.0.0.1`.

```bash
bun dynwork/script/sp-local.ts up       # start PostgreSQL and both instances, wait until they answer
bun dynwork/script/sp-local.ts seed     # user, PAT, exchange code and content on each instance
bun dynwork/script/sp-local.ts check    # health, PAT to JWT, signed manifest, ETag and 304, content counts
bun dynwork/script/sp-local.ts status   # containers and health
bun dynwork/script/sp-local.ts code     # fresh exchange code for both (or `code alpha`)
bun dynwork/script/sp-local.ts capture  # observe alpha's browser device link, rewrite fixtures/device-link.json
bun dynwork/script/sp-local.ts mobile-auth-probe  # can a phone sign in with the instance's OAuth? rewrites fixtures/mobile-auth.json
bun dynwork/script/sp-local.ts down     # remove containers, volumes and .env.local
cd dynwork/test/sp-local && bun test    # unit tests of the script's helpers
```

The compose project is `dynwork-sp-local`, so `down` only removes what `up` created.

## A second stack

Another session or plan that needs its own instances sets two variables on every command, so it never touches the
containers, volumes or env file of the default stack:

```bash
export SP_LOCAL_PROJECT=dynwork-sp-mobile SP_LOCAL_PORT_BASE=18201
bun dynwork/script/sp-local.ts up       # alpha on :18201, beta on :18202, secrets in .env.dynwork-sp-mobile.local
```

`SP_LOCAL_PROJECT` is the compose project (lowercase letters, digits, `-` and `_`; default `dynwork-sp-local`) and
`SP_LOCAL_PORT_BASE` the first port `up` tries (default 18101). A project other than the default keeps its secrets in
`.env.<project>.local` (gitignored); the default keeps `.env.local`. `down` removes only that project. Run it from the
same shell as `up`, or the variables are missing and `down` addresses the default stack. Requires Docker with access to
ghcr.io (the image is public). The first `up` pulls about 2 GB and takes around a minute to boot.

## What the image needs

Learned from the image's entrypoint and its CLI help; nothing here comes from the Dynapps environments.

| Variable                   | Why                                                                                                             |
| -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`             | one database per instance (`alpha`, `beta`); migrations run at boot                                             |
| `SYSTEMPROMPT_ADMIN_EMAIL` | the administrator `admin setup` creates on first boot (`admin@<instance>.dynapps.test`)                         |
| `ANTHROPIC_API_KEY`        | at least one provider key must be set or the entrypoint exits. A random dummy is enough: no model call is made  |
| `ENTRA_OIDC_CLIENT_SECRET` | the shipped Entra OIDC config is enabled and the server refuses to boot without a client secret. A random dummy |
| `EXTERNAL_URL`             | the instance's public URL, here `http://127.0.0.1:<port>`                                                       |

`SP_DB_PASSWORD`, the dummy provider key, the dummy Entra secret and the two host ports are generated by `up` into
`.env.local`. Ports start at 18101 and skip 17495 (DynWork's service), 18080 and 15000 (other containers on this Mac)
and anything already listening. The entrypoint writes the profile, its secrets and the signing key inside the
container: they survive `docker compose restart` but not a re-created container, which then signs with a new key (run
`down` and `up` instead of `up --force-recreate`).

## What `seed` writes

Per instance, using the instance's own CLI (`docker compose exec <instance> /app/bin/systemprompt ...`):

- the user `dev@dynapps.test` (`admin users create`), role `user`;
- a PAT (`admin users api-key issue`; the secret is printed once and kept in `.env.local`);
- an exchange code (`admin bridge issue-code`). It lives 10 minutes and works once; `sp-local.ts code` issues another;
- content: the tree in `content/<instance>` goes through `core marketplace import --strict`, the agent through
  `admin agents create`, and the result is copied into `/app/services` and applied with `admin config apply`. The
  instance reads its services tree at boot, so seed restarts it once. A second `seed` finds the content and skips this.

`.env.local` keys: `SP_<ALPHA|BETA>_URL`, `_USER_EMAIL`, `_USER_ID`, `_PAT`, `_EXCHANGE_CODE`,
`_EXCHANGE_CODE_EXPIRES`, plus the generated secrets above. Never print a whole PAT or JWT.

## Content

What a user receives is decided by entitlement, not by what the image ships. A plain `user` only gets the
`dynapps-commons` marketplace (one skill, `who_am_i`). Each instance therefore adds its own marketplace, open to the
`user` role through the marketplace sidecar:

|            | alpha                                           | beta                         |
| ---------- | ----------------------------------------------- | ---------------------------- |
| skills     | `alpha_review`, `alpha_notes`                   | `beta_review`, `beta_triage` |
| agent      | `alpha_helper`                                  | `beta_helper`                |
| MCP server | `alpha-docs` (placeholder URL, nothing listens) | `beta-docs`                  |
| rule       | `alpha_conventions`                             | `beta_conventions`           |

`/v1/bridge/manifest` for `dev@dynapps.test` then carries 3 skills (the two plus `who_am_i`), 1 agent, 1 managed MCP
server and 1 rule per instance. The `core skills` CLI group is read-only, which is why content is authored as files.

To change content by hand: edit the files under `/app/services` in the container and run `admin config apply`. A
skill (its directory under `skills/` plus its id in the plugin's `skills.include`) is served by the running instance
10 to 20 seconds after the apply, and leaves the manifest as quickly once removed (observed in phase 14; the e2e does
this). Other content may still need `docker compose -p dynwork-sp-local restart <instance>`.

## What `capture` records

`capture` drives alpha's browser device link end to end and writes `fixtures/device-link.json`: the login gate, the
consent page as rendered, every page and API request the browser made (query names only), the loopback callback, the
code-to-PAT-to-JWT exchange and a set of experiments (which redirects the page accepts, `state`, Deny, the paste flow
without a redirect, `/v1/auth/bridge/session`, bad and reused codes, the `admin bridge issue-code` flow, a revoked PAT).
No code, PAT or JWT reaches the file: values are replaced by what they are, and the command refuses to write if one of
the run's secrets would. With a fixture already there it says which entries changed. The contract it supports is
`dynwork/packages/sp-client/PROTOCOL.md`.

The admin login is Entra only, so the capture signs in another way: `admin users webauthn generate-setup-token` gives
a passkey link, a virtual authenticator in Chromium registers a passkey on `http://localhost:<port>` (the WebAuthn
relying party is `localhost`; on `127.0.0.1` the browser refuses it), the core OAuth authorize page signs in with it
for a dynamically registered public client, and the resulting JWT goes as a bearer on the browser's requests to the
instance. It leaves a passkey and an OAuth client on alpha each run, and revokes the PATs it mints (named "DynWork
capture").

Playwright comes from `packages/app` (dynwork has no dependency on it). When the Chromium build of the pinned
Playwright is not downloaded, the capture uses the installed Google Chrome.

## What `mobile-auth-probe` records

`mobile-auth-probe` asks both instances whether a phone can sign in with their OAuth server (RFC 8252 native app) and
writes `fixtures/mobile-auth.json` with a `verdict`: `core OAuth usable` or `extension endpoint needed`. Per instance it
reads the discovery documents, registers public clients for a set of redirect URIs (as `native` and as `web`), asks
`authorize` for a set of redirect, PKCE and `state` variations without signing in, then signs in with the same passkey as
`capture` and runs the whole round trip for `dynwork://auth/callback` and for a loopback redirect: callback, token,
refresh and its rotation, a code used twice, a wrong verifier, the OAuth token on the bridge routes, and revoke. It
removes the clients it registered. As with `capture`, nothing secret reaches the file and a changed answer is reported
by leaf. The contract it supports is section 10 of `dynwork/packages/sp-client/PROTOCOL.md`.

## Limits

- No model calls: there is no real provider key (decision: out of scope for the harness).
- The browser device link page (`/bridge-auth/device-link`) sits behind the admin login, which here is Entra ID
  (Dynapps' tenant, unreachable). Only `capture` gets past it, with the passkey login above; other phases take exchange
  codes from `admin bridge issue-code` (`sp-local.ts code`).
